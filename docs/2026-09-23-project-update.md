## 1. Executive Summary

**สรุป:**

> ระบบนี้ย้ายแบบฟอร์มเบิกค่าใช้จ่ายของบริษัทจากกระดาษ/Excel มาเป็นเว็บ ให้พนักงานกรอก บันทึก พิมพ์ และเซ็นออนไลน์ได้ โดยผู้ดูแลสร้างและแก้ไขแบบฟอร์มเองได้โดยไม่ต้องแก้โค้ด ผู้ใช้หลักคือพนักงานที่เบิกค่าใช้จ่ายและฝ่ายบัญชี
>
> ขณะนี้ระบบ **ขึ้น Production และมีการใช้งานจริงแล้ว** สิ่งที่ทำได้จริงคือ สร้าง–บันทึก–แก้ไข–แนบไฟล์–พิมพ์/บันทึก PDF–เซ็นออนไลน์–ดูประวัติ และผู้ดูแลตั้งค่าแบบฟอร์มเองได้
>
> **สิ่งสำคัญที่สุดที่ยังขาดคือ ระบบไม่มี Workflow การอนุมัติ** (ไม่มีสถานะ ส่งอนุมัติ / อนุมัติ / ตีกลับ / ปฏิเสธ / บันทึกจ่าย) ปัจจุบันใช้ "ช่องลายเซ็น" แทน ซึ่งไม่เท่ากับการอนุมัติตามอำนาจ และ **ยังไม่มีผู้มีอำนาจฝ่ายบัญชีคนใดยืนยันกฎภาษี/วงเงิน/อำนาจอนุมัติเลยแม้แต่ข้อเดียว**
>
> **ขั้นถัดไปเพียงเรื่องเดียว:** ระบุชื่อ Business Owner ฝ่ายบัญชี และให้ยืนยัน Business Rules ในข้อ 8 เป็นลายลักษณ์อักษร

## 3. Problem และขอบเขตของระบบ

### 3.1 ปัญหาปัจจุบัน

**รายละเอียด:**

หลักฐานที่ยืนยันได้: ทีมบัญชีส่งไฟล์สแกน "ใบขออนุมัติเบิกค่าใช้จ่าย" (รหัส GAC6709-003) ที่กรอกด้วยมือ พิมพ์ออกกระดาษ และเซ็นด้วยปากกา มาให้ใช้เป็นต้นแบบ แสดงว่ากระบวนการเดิมเป็นกระดาษ

🤖 **ข้อสันนิษฐานของ AI (ยังไม่มีคนยืนยัน):** ปัญหาน่าจะอยู่ที่การตามเอกสาร การคำนวณยอด/ภาษีด้วยมือ และการตรวจย้อนหลัง

⚠️ **ต้องกรอกโดยผู้ที่รู้กระบวนการจริง:**
- ผู้ขอต้องทำอะไรบ้าง ส่งให้ใครตรวจ/อนุมัติตามลำดับใด
- ฝ่ายบัญชีรับข้อมูลอย่างไร และบันทึกเข้าระบบบัญชีอย่างไร
- **Baseline: จำนวนคำขอต่อเดือน, ระยะเวลาต่อ 1 คำขอ, Error ที่พบบ่อย** — ปัจจุบัน**ไม่มีข้อมูล Baseline เลย** จึงยังวัดไม่ได้ว่าระบบช่วยลดอะไรลงได้จริงหรือไม่

### 3.2 วัตถุประสงค์

⚠️ ต้องกรอกโดย Project Owner — ต้องระบุเป็นผลลัพธ์ที่วัดได้ ไม่ใช่ "สร้างแอป"
🤖 ข้อสันนิษฐาน: ลดเวลาจัดทำเอกสาร ลดเอกสารตกหล่น และให้ตรวจย้อนหลังได้

### 3.3 In Scope

- [x] แบบฟอร์มเบิกค่าใช้จ่าย
- [x] แบบฟอร์มกลางประเภทอื่น: ผู้ดูแลสร้างแบบฟอร์มใหม่เองได้ (ปัจจุบันมีเช่น ใบรับเงินคืนเข้าบริษัท GAC6709-008, ใบอนุมัติค่าใช้จ่าย GAC69-005)
- [ ] **Workflow การตรวจสอบและอนุมัติ — ยังไม่มีในระบบ** (มีเฉพาะช่องลายเซ็น ดูข้อ 5)
- [x] แนบเอกสาร/ใบเสร็จ
- [ ] แจ้งเตือน — มีเฉพาะตัวเลขแจ้งบนเมนู "รอฉันเซ็น" ในแอป ไม่มีอีเมล/LINE/Push
- [x] ติดตามสถานะ (เฉพาะสถานะลายเซ็น: เสร็จสิ้น / รอลายเซ็น / เซ็นครบ)
- [x] ประวัติและ Audit Trail (เก็บทุกเวอร์ชันของเอกสารที่แก้ไข)
- [ ] **Report / Export สำหรับบัญชี — ยังไม่มี** (ส่งออกได้เฉพาะ PDF ทีละใบผ่านการพิมพ์)
- [x] ผู้ดูแลสร้าง/แก้แบบฟอร์มเองได้ (Form Engine)

### 3.4 Out of Scope

ยังไม่ครอบคลุม และผู้ใช้/ผู้บริหารไม่ควรเข้าใจว่าทำได้:
- ไม่เชื่อมต่อระบบบัญชี/ERP ใด ๆ
- ไม่มีการบันทึกการจ่ายเงินหรือสถานะจ่ายแล้ว
- ไม่มีการอนุมัติตามวงเงิน/ลำดับขั้น
- ไม่มีรายงานสรุปหรือ Export สำหรับปิดบัญชี
- ไม่มีแอปมือถือ (เป็นเว็บที่เปิดบนมือถือได้ แต่ยังไม่ได้ทดสอบจริงจัง)

## 4. ผู้ใช้งานและสิทธิ์

ระบบมี **3 ระดับสิทธิ์** เท่านั้น ไม่ได้แยก Approver / Accounting Reviewer / Auditor ออกจากกัน

| Role | ผู้ใช้งานตัวอย่าง | ทำอะไรได้ | ข้อมูลที่มองเห็น | สถานะการพัฒนา/ทดสอบ |
|---|---|---|---|---|
| Requester (`employee`) | พนักงานทั่วไป | สร้าง/แก้/ลบเอกสารของตนเอง, แนบไฟล์, พิมพ์, ส่งให้คนอื่นเซ็น, เซ็นช่องที่ถูกมอบหมาย | เฉพาะเอกสารของตนเอง + เอกสารที่ถูกมอบหมายให้เซ็น | ใช้งานได้จริงใน Production · บังคับสิทธิ์ที่ฐานข้อมูล (RLS) |
| Approver | หัวหน้างาน/ผู้บริหาร | **ไม่มี Role นี้ในระบบ** — ผู้อนุมัติคือ "ผู้ถูกมอบหมายให้เซ็น" ซึ่งเป็นพนักงานทั่วไป | — | **ยังไม่ได้พัฒนา** |
| Accounting Reviewer | ฝ่ายบัญชี | **ไม่มี Role นี้แยกต่างหาก** ปัจจุบันต้องให้สิทธิ์ Admin แทน | — | **ยังไม่ได้พัฒนา** |
| Admin (`admin`, "Account Admin") | ผู้ดูแลระบบ | ทุกอย่างของพนักงาน + จัดการพนักงาน/กลุ่ม/แผนก, สร้างและแก้แบบฟอร์ม, ดูเอกสารทุกคน, เซ็น/ลบลายเซ็นบนเอกสารตนเอง | เอกสารทุกคน | ใช้งานได้จริงใน Production |
| Super Admin (`isSuperAdmin`) | บัญชี `admin001` | ทุกอย่างของ Admin + ตั้งรหัสผ่านให้ผู้อื่น + เปลี่ยนชื่อผู้ใช้ | เหมือน Admin | ใช้งานได้จริงใน Production |
| Auditor / Viewer | — | **ไม่มี Role นี้** | — | **ยังไม่ได้พัฒนา** |

> **ข้อควรระวัง:** การจะให้ฝ่ายบัญชีตรวจเอกสารของคนอื่นได้ ต้องให้สิทธิ์ Admin ซึ่งทำให้แก้ไขทุกอย่างในระบบได้ด้วย — ไม่มีการแยกหน้าที่ (Segregation of Duties)

## 5. Workflow ปัจจุบันของแอป

### Workflow ที่ระบบทำได้จริงตอนนี้

```text
พนักงานเลือกแบบฟอร์ม
→ กรอกข้อมูล + แนบไฟล์
→ บันทึก (ระบบออกเลขที่เอกสารอัตโนมัติ)
→ [ทางเลือก] ส่งให้คนอื่นเซ็น (เลือกผู้เซ็นรายช่อง)
→ ผู้ถูกมอบหมายเห็นในเมนู "รอฉันเซ็น" แล้วกดเซ็น (แปะรูปลายเซ็นที่อัปโหลดไว้)
→ พิมพ์ / บันทึกเป็น PDF
→ จบ (ไม่มีสถานะหลังจากนี้)
```

### Workflow เป้าหมายที่ยังทำไม่ครบ

```text
พนักงานสร้างคำขอ            ✅ ทำได้
→ บันทึกร่าง                 ⚠️ บันทึกได้ แต่ไม่มีแนวคิด "ร่าง" แยกจาก "ส่งแล้ว"
→ ส่งคำขอ                    ❌ ไม่มี
→ หัวหน้างานอนุมัติ           ❌ ไม่มี (มีแค่ "เซ็น" ซึ่งไม่ผูกกับอำนาจอนุมัติ)
→ ฝ่ายบัญชีตรวจเอกสาร         ❌ ไม่มี
→ อนุมัติจ่าย / ตีกลับ / ปฏิเสธ ❌ ไม่มีทั้งสามอย่าง
→ บันทึกการจ่าย              ❌ ไม่มี
→ ปิดรายการ                  ❌ ไม่มี
```

> **หมายเหตุสำคัญ:** ระบบเคยมีโครง Workflow อนุมัติ (ส่งอนุมัติ → routing ตามแผนก → อนุมัติ/ตีกลับ) อยู่ในไฟล์ `supabase/approval-migration.sql` แต่**ถูกถอดออกทั้งหมด**และแทนที่ด้วยระบบลายเซ็นออนไลน์ (`supabase/signature-system.sql`) จึงไม่มีการอนุมัติในระบบปัจจุบัน

### สถานะและเงื่อนไขการเปลี่ยนสถานะ

ระบบมีสถานะจริงเพียง **3 สถานะ** ซึ่งคำนวณจากลายเซ็น ไม่ใช่จาก Workflow

| สถานะ | ความหมาย | ใครเปลี่ยนได้ | เงื่อนไข | ทำงานจริงแล้วหรือยัง |
|---|---|---|---|---|
| เสร็จสิ้น (`done`) | บันทึกแล้ว ไม่มีใครถูกขอให้เซ็น | เจ้าของเอกสาร | ไม่มีรายการลายเซ็น | ✅ ใช้งานได้จริง |
| รอลายเซ็น (`pending`) | มีผู้ถูกมอบหมายแต่ยังเซ็นไม่ครบ | เจ้าของเอกสาร (ส่ง) / ผู้เซ็น (เซ็น) | มีอย่างน้อย 1 ช่องยังไม่เซ็น | ✅ ใช้งานได้จริง |
| เซ็นครบ (`signed`) | ทุกช่องที่มอบหมายเซ็นครบ | ผู้เซ็นคนสุดท้าย | ทุกช่อง = signed | ✅ ใช้งานได้จริง |
| Draft / Submitted / Pending Approval / Returned / Rejected / Accounting Review / Approved for Payment / Paid / Closed / Cancelled | — | — | — | ❌ **ไม่มีในระบบทั้งหมด** |

**สิ่งที่ทำงานจริงแล้ว:** ผู้ดูแลสร้างฟอร์มใหม่ กำหนดคอลัมน์และสูตรคำนวณ ตั้งช่องลายเซ็น หัวข้อ หมายเหตุ และความกว้างคอลัมน์ได้เองทั้งหมดผ่านหน้าจอ โดยไม่ต้องแก้โค้ด — ยืนยันจากการตั้งค่าฟอร์ม GAC69-005 ให้ตรงกับกระดาษของทีมบัญชีได้สำเร็จ

### 9.3 Data Control

- **ป้องกันเลขคำขอซ้ำอย่างไร:** ฟังก์ชัน `next_doc_number()` ในฐานข้อมูลเพิ่มเลขแบบ atomic (`INSERT ... ON CONFLICT DO UPDATE`) และตั้งแต่ 2026-09-18 ตาราง `counters` ถูกปิดไม่ให้ผู้ใช้แก้โดยตรง — **ยืนยันแล้วด้วยการยิง API จริง** (ตอบ 401 permission denied)
- **ป้องกันการส่งคำขอซ้ำอย่างไร:** มีเฉพาะการกันกดปุ่มซ้ำในหน้าจอ · **ไม่มีการตรวจซ้ำฝั่งฐานข้อมูล**
- **ตรวจ Required/Missing Data อย่างไร:** ตรวจในหน้าจอเท่านั้น (ชื่อ/นามสกุล/ตำแหน่ง และยอดรวม > 0) · **ฐานข้อมูลไม่บังคับ**
- **เก็บประวัติการแก้ไขอย่างไร:** ทุกครั้งที่เนื้อหาเปลี่ยน จะบันทึกสำเนาทั้งฉบับลง `submission_versions` พร้อมชื่อผู้แก้และเวลา · ข้อจำกัด: การบันทึกประวัติเป็นแบบ "ทำได้ก็ทำ" ถ้าล้มเหลวจะไม่แจ้งเตือนและประวัติหายเงียบ ๆ
- **ผู้ใช้ลบรายการได้หรือไม่:** ได้ — เจ้าของและ Admin ลบเอกสารได้ (หน้าจอซ่อนปุ่มลบเมื่อมีลายเซ็นแล้ว) · **ลบแล้วหายถาวร ไม่มีถังขยะ**
- **Backup และ Restore อย่างไร:** ใช้ backup อัตโนมัติของ Supabase ตาม plan เท่านั้น · ⚠️ **ไม่เคยทดสอบ Restore** · ⚠️ ต้องกรอกว่า Supabase plan ปัจจุบันเก็บ backup ย้อนหลังกี่วัน
- **Retention ระยะเวลาเท่าไร:** ⚠️ **ไม่มีนโยบาย**
- **Export/ส่งต่อให้บัญชีอย่างไร:** พิมพ์หรือบันทึก PDF ทีละใบ · **ไม่มีการส่งออกเป็นไฟล์ข้อมูล**

AI รันคำสั่งติดตั้ง dependency ขณะที่ dev server ของผู้พัฒนาทำงานอยู่ **ทำให้หน้าจอขาวทั้งหมด** ต้องรีสตาร์ท<br>4. AI เกือบส่ง SQL ที่มี JSON ผิดรูปแบบ (ขึ้นบรรทัดจริงในสตริง JSON) ซึ่งจะรันไม่ผ่าน — จับได้จากการตรวจก่อนส่ง |

## ภาคผนวก: สิ่งที่เอกสารฉบับนี้ยังตอบไม่ได้

เพื่อความโปร่งใส ผู้ช่วย AI ที่ช่วยร่างเอกสารนี้**ไม่มีสิทธิ์เข้าถึงฐานข้อมูล Production และไม่มีบัญชีผู้ใช้** จึงตรวจสอบไม่ได้และ**ไม่ได้เดา**ในเรื่องต่อไปนี้:

2. ข้อมูลในระบบเป็นข้อมูลจริงหรือทดสอบ

4. ไฟล์ seed แบบฟอร์มอื่น ๆ ถูกนำขึ้นฐานข้อมูลแล้วหรือยัง
5. Supabase plan ปัจจุบันและระยะเวลาเก็บ backup
6. ชื่อบุคคลทั้งหมด (ผู้พัฒนา, Owner, ผู้อนุมัติ Requirement)
7. Baseline ของกระบวนการเดิม (จำนวนคำขอ/เดือน, เวลาต่อคำขอ)
8. การทดสอบบนมือถือ, การทดสอบสิทธิ์ไฟล์แนบ และการทดสอบพร้อมกันหลายคน
