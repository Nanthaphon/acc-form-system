# ปล่อยขึ้นระบบจริง — ทำตามลำดับนี้

> **ทำคนเดียว ใช้แค่ 2 กฎนี้พอ**
> - **แก้แต่โค้ด** (ไม่มีไฟล์ SQL ใหม่) → push → รอ CI เขียว → ขึ้น `main` ได้เลย · พังก็ย้อน deployment ใน 30 วินาที
> - **มีไฟล์ SQL ใหม่** → รัน SQL ที่ staging ลองก่อน → `npm run backup` → รัน SQL ที่ของจริง → ค่อย push
>
> ที่เหลือข้างล่างคือฉบับเต็ม ใช้เมื่องานใหญ่หรือมีคนช่วยทำหลายคน

ระบบนี้มีผู้ใช้จริงและข้อมูลที่กู้คืนไม่ได้ (Supabase แผนฟรีไม่มีสำรองอัตโนมัติ)
ลำดับข้างล่างคือสิ่งที่ทีมซอฟต์แวร์ทั่วไปทำก่อนปล่อยของ ย่อให้เหลือเท่าที่โปรเจกต์ขนาดนี้ต้องใช้จริง

## 1. ระหว่างทำงาน — ไม่แก้บน `main`

```bash
git switch -c feat/ชื่องาน
```

`main` = สิ่งที่อยู่บนเว็บจริงตอนนี้ ทุกอย่างที่ยังไม่พิสูจน์ อยู่บน branch ของตัวเอง

## 2. ตรวจเองก่อน (เครื่องตัวเอง)

```bash
npm test && npm run build && npm run lint
```

เปลี่ยนหน้าจอ → ดูด้วยตาในโหมดเดโม (`npm run dev:demo`) หรือระบบทดสอบ (`npm run dev:both` → พอร์ต 5175)

## 3. ตรวจอัตโนมัติ (CI)

push ขึ้น GitHub แล้ว `.github/workflows/ci.yml` จะรัน lint + เทสต์ + build ให้เอง
**ต้องเป็นเครื่องหมายถูกสีเขียวเท่านั้นจึง merge** — ถ้าแดง แก้ให้เขียวก่อน

## 4. มี SQL ใหม่ไหม

| | ทำอะไร |
|---|---|
| ก. | รันไฟล์ SQL ที่ **project ทดสอบ** ก่อน แล้วลองใช้งานจริงบนพอร์ต 5175 |
| ข. | SQL ต้อง **เพิ่มอย่างเดียว** (`add column if not exists`, `create or replace`) ห้ามลบ/เปลี่ยนชื่อคอลัมน์ที่ใช้อยู่ |
| ค. | แอปต้องทำงานได้ทั้งก่อนและหลังรัน SQL (โค้ดในโปรเจกต์นี้มีกลไกรองรับคอลัมน์ที่ยังไม่มีอยู่แล้ว) |

เหตุผล: ถ้า SQL กับโค้ดต้องขึ้นพร้อมกันเป๊ะ ๆ ช่วงไม่กี่นาทีที่ต่างกันจะทำให้ระบบจริงพัง

## 5. ให้คนใช้จริงลองก่อน (UAT)

push branch → Vercel สร้างลิงก์ Preview ให้เอง → ส่งลิงก์นั้นให้คนที่จะใช้ลอง
(ลิงก์ Preview ต่อกับฐานข้อมูลทดสอบ ถ้าตั้งค่า Environment Variables ตาม `docs/environments.md` ข้อ 2.6)

## 6. สำรองข้อมูลจริง (เฉพาะรอบที่มี SQL)

```bash
npm run backup
```

ได้ไฟล์ใน `backups/` (Git ไม่เก็บให้) — ก๊อปไปไว้ OneDrive ของบริษัท
ครั้งแรกต้องติดตั้ง PostgreSQL (เฉพาะ Command Line Tools) และสร้าง `.env.backup.local` หนึ่งบรรทัด
รันคำสั่งแล้วมันจะบอกเองว่าขาดอะไร

ไฟล์สำรองมีข้อมูลพนักงานและเอกสารจริง — ห้ามใส่ใน Git ห้ามส่งทางแชท
(ไฟล์แนบรูปใบเสร็จอยู่ใน Storage แยก ไม่อยู่ในไฟล์นี้)

## 7. ปล่อยขึ้นจริง

1. รัน SQL ที่ **project จริง** (ถ้ามี)
2. merge เข้า `main` → Vercel deploy ให้เองใน ~1 นาที
3. เปิดเว็บจริง ลองสิ่งที่เพิ่งแก้ 1 รอบ
4. เขียนประกาศใน `src/shared/announcements.ts` ให้ผู้ใช้รู้ว่าอะไรเปลี่ยน (ขึ้นไปพร้อมโค้ด)

## 8. ถ้าพัง

- **โค้ดพัง** → Vercel → Deployments → deployment ก่อนหน้า → Promote to Production (กลับคืนใน ~30 วินาที)
- **ข้อมูลพัง** → กู้จากไฟล์สำรองข้อ 6

## สิ่งที่ยังไม่มีในโปรเจกต์นี้ (และยังไม่จำเป็นตอนนี้)

| ของที่ทีมใหญ่ใช้ | ทำไมยังไม่ต้อง |
|---|---|
| เทสต์แบบกดจริงทั้งระบบ (E2E เช่น Playwright) | เทสต์ 670 ข้อครอบคลุมตรรกะแล้ว และผู้ใช้จริงลองบน Preview ได้ |
| ปล่อยทีละ % ของผู้ใช้ (canary) | ผู้ใช้หลักสิบคนในบริษัทเดียว ปล่อยทีเดียวแล้วดูแลได้ |
| ระบบแจ้งเตือนเมื่อเว็บล่ม (monitoring) | ยังไม่มี — ถ้าเริ่มมีคนใช้เยอะ ค่อยเพิ่ม Sentry หรือ Vercel Analytics |
| สำรองข้อมูลอัตโนมัติรายวัน | ต้องอัปเกรด Supabase เป็นแผน Pro |
